# RepoCheatMenu — заметки для будущих сессий

BepInEx-чит для R.E.P.O. (Unity + Photon PUN2). Раньше — личное использование с друзьями; с 2026-10-06
продаётся на FunPay (лот продавца Kolyagames, автовыдача ключей) с лицензиями на сайте `projects\repo-site`
(логин/пароль, ключи, проверка в лаунчере). Прежнее условие «не продаётся» снято самим пользователем.

## Ground truth

Все технические утверждения проверяются по декомпилированному коду, а не по памяти/положениям:
- `decompiled/` — Assembly-CSharp (сама игра)
- `decompiled-libs/` — Photon, Steamworks, Sirenix и т.д.

Если утверждение нельзя подтвердить grep'ом по этим папкам — не реализуй его как факт, скажи прямо, что не подтверждено (см. случай с `PlayerAvatarSetColor` из D4rkks — такого метода в декомпиле нет, фичу не добавляли).

## Архитектура фичи (как пристыковать новую функцию)

Тумблер/тикающая функция — 4 места:
1. Файл-хак (`XxxHack.cs`) — статический класс, метод `Apply()`, читает `CheatState.Xxx.Value`.
2. `CheatState.cs` — поле `ConfigEntry<T>`, `config.Bind(...)` с описанием, опционально `KeybindManager.RegisterToggle`/`RegisterAction`.
3. `Patches.cs` — либо `RunSafe("Имя", XxxHack.Apply)` в `ApplyStats()` (тикает каждый кадр), либо Harmony-патч (`[HarmonyPatch(typeof(Игра), "Метод")]`), если нужно перехватить конкретный игровой метод, а не просто опрашивать состояние.
4. `OverlayUI.cs` — строка `AddToggleRow`/`AddButtonRow`/`AddFloatStepperRow`/`AddColorCycleRow` внутри нужной вкладки (`AddTab("Имя", () => {...})`).

Свой файл заводится только когда логика самостоятельна (не захламляет существующий hack-файл).

Общие хелперы: `GameReflect` (доступ к private/internal полям игры через рефлексию), `PlayerTargets` (общий пикер цели — `Picked()`, `AliveOthers()`, `NameOf()`).

## Модель безопасности Photon RPC (ключевое знание проекта)

Три уровня защиты RPC-методов, различай их явно при анализе новой фичи:
- **Правильно защищено**: проверяет `_info.Sender` (`SemiFunc.MasterOnlyRPC`, `OwnerOnlyRPC`, `MasterAndOwnerOnlyRPC`) — сервер сам определяет отправителя, подделать нельзя. Для гостя — стена, если только он не хозяин/владелец объекта.
- **Неправильно защищено (дыра)**: проверяет только контекст исполнения (`SemiFunc.IsMasterClientOrSingleplayer()`), не отправителя — гость может вызвать и получить эффект НА МАШИНЕ ХОСТА, если хост тоже это выполнит.
- **Не защищено вообще**: применяется у любого, кто получил RPC и совпадает нужное условие (например `HealOtherRPC` — только `photonView.IsMine` на стороне получателя, кто угодно может отправить).

**Важное открытие (из GameTools)**: `SemiFunc.MasterOnlyRPC` сама патчится Harmony-патчем — `MasterOnlyRpcSelfBypassPatch` в `Patches.cs`, тумблер `CheatState.MasterRpcSelfBypass`. Патч заставляет проверку проходить НА ТВОЕЙ МАШИНЕ, если `_info.Sender == PhotonNetwork.LocalPlayer` — то есть открывает эффекты, которые раньше отбрасывались локально у гостя (пример: `ReviveHack.ReviveSelf` — `PlayerAvatar.ReviveRPC` защищён только этой проверкой, без доп. гейтов). Работает только локально — то, что видит ДРУГОЙ игрок, не меняется (у них своя, непатченная проверка).

## Не трогай PhotonNetwork раньше игры (правило, подтверждённое трижды)

`PhotonNetwork.NetworkingClient` (и любой доступ, который заставляет CLR инициализировать класс `PhotonNetwork`) нельзя трогать раньше, чем игра сама это сделает в `NetworkConnect.Start()` → `DataDirector.PhotonSetRegion/Version/AppId()`. Сам факт обращения к статике `PhotonNetwork` (даже просто прочитать `NetworkingClient` на `null`, даже просто прицепить Harmony-патч к любому методу, объявленному прямо на этом классе) форсирует её статический конструктор, который строит `NetworkingClient = new LoadBalancingClient(...)` — с дефолтными, ненастроенными параметрами. Когда игра позже пытается настроить СВОЙ клиент, она находит «уже занято», и реальный коннект-флоу зависает навсегда на `OnConnectedToMaster` — без единой ошибки в логе, тихо. Симптом в игре: список серверов/регионов вечно крутится (спиннер), хотя без мода грузится за секунды.

Плагин тикает (через `TimeTickPatch` на `UnityEngine.Time.deltaTime`) с самого `Plugin.Awake()` — то есть с первого кадра, задолго до того как игрок дойдёт до входа в лобби. Любой код, который трогает `PhotonNetwork` без разбора момента, подрывается.

Три подтверждённых случая одного и того же бага в этом проекте:
1. **`PacketTestHack.Init()`** — изначально написан пустым именно из-за этого (см. комментарий в файле) — никогда не наступал на грабли, потому что подписка на события отложена до `EnsureSubscribed()`, вызываемого только когда `PhotonNetwork.InRoom` уже true.
2. **`NetworkDiagnostics.Apply()`** — читал `PhotonNetwork.NetworkingClient` ДО проверки своего тумблера (`CheatState.NetworkDiagnostics.Value`), каждый тик, с первого кадра, независимо от того, включена ли функция. Фикс — проверка тумблера строго ДО обращения к `PhotonNetwork`.
3. **`AntiCrashExecuteRpcPatch`/`AntiCrashOnEventPatch`** — были атрибутно патчены (`[HarmonyPatch(typeof(PhotonNetwork), "ExecuteRpc"/"OnEvent")]`), что цепляется через `PatchAll()` в `Awake()`. Тут тумблер (`CheatState.AntiCrash.Value`) не спасал вообще, потому что проверка живёт ВНУТРИ Prefix-метода, а сам факт прикрепления патча — до всякого Prefix, безусловно. Фикс — убрали атрибут у класса, патчат вручную через `harmony.Patch(...)` внутри `DeferredAntiCrashInstallPatch` — постфикс на `[HarmonyPatch(typeof(NetworkConnect), "Start")]`, то есть строго после того как игра сама настроила регион/AppId. Это единственный из трёх случаев, который не лечится проверкой тумблера — нужен именно отложенный `harmony.Patch()`.

Практическое правило для новых фич: если код трогает `PhotonNetwork.*` (напрямую или через `[HarmonyPatch(typeof(PhotonNetwork), ...)]`) — либо гейтуй тумблером ДО первого обращения (как в случае 2), либо, если это Harmony-атрибут прямо на классе `PhotonNetwork`, патчи вручную и отложенно через `NetworkConnect.Start()` как якорь (как в случае 3, `DeferredAntiCrashInstallPatch` — использовать как образец).

## CustomGui — собственный immediate-mode рендерер (второе меню + HUD)

Параллельно старому uGUI-меню (`OverlayUI.cs`, RightShift) существует второе меню на собственном рендерере (`CustomOverlayUI.cs`, F6) и постоянный игровой HUD (`PlayerHud.cs`) — оба рисуются через `CustomGui.cs`, свой генератор меша (не Unity `Text`/`Image`), с нуля, без копирования чужого кода (RepoHax/GameTools — только сама идея "свой велосипед", не их реализация).

- **Один общий кадр на все рисующие системы**: `HudRoot.cs` владеет ЕДИНСТВЕННЫМ канвасом + парой поверхностей (`CustomGui.Init`), и `HudRoot.Tick()` — единственное место, где вызываются `CustomGui.BeginFrame()`/`EndFrame()` за реальный кадр. `PlayerHud.Draw()` рисует первым (всегда), `CustomOverlayUI.DrawIfVisible()` — поверх, если меню открыто. Причина: `CustomGuiGraphic.Clear()` очищает ВЕСЬ меш на каждый `BeginFrame()` — два независимых цикла Begin/End в одном визуальном кадре стирают друг друга, а не накладываются. Если добавляешь новую рисующую систему (третий виджет-слой и т.п.) — она должна дорисовываться в ЭТОТ же кадр, не заводить свой Begin/End.
- **Иконки предметов — не через CustomGui**: `CustomGuiGraphic` умеет только сплошной `Texture2D.whiteTexture` (для rect) или атлас шрифта (для текста) — произвольный `Sprite` (иконка предмета) через неё не нарисовать. Решение — обычные Unity `Image`, пул объектов под `HudRoot.IconLayer` (тот же `RectTransform`-сетап: anchorMin=0, anchorMax=1, pivot=(0,0), что и у поверхностей CustomGui — поэтому `Rect` из `CustomGui.Rect(...)` совпадает по координатам с `anchoredPosition`/`sizeDelta` для дочернего Image с точечным якорем (0,0) и своим pivot (0,0)).
- **Исправленный баг в `AddRoundedRect`**: угловые дуги были повёрнуты на 90° (например нижне-правый угол шёл 0°→90° вместо 270°→360°) — конечная точка дуги попадала не на границу прямоугольника, а внутрь него, и веерная триангуляция из центра давала самопересекающуюся «бабочку» (видимый диагональный Х-разрыв на крупных панелях). Баг был во ВСЕХ скруглённых элементах с самого начала (в т.ч. старое меню), но на маленьких кнопках почти незаметен. Исправлено — 270°/0°/90°/180°, проверено вручную на конкретных координатах.
- **`CustomGui.Text` не поддерживал `\n`** — `GetCharacterInfo('\n')` просто проваливался как для любого неизвестного глифа, курсор сдвигался на полшрифта вбок вместо переноса строки. Тихо ломало ВСЕ многострочные вызовы (`LiveInfo` в `CustomOverlayUI` — статистика NetworkDiagnostics/AntiCrash, обе двухстрочные), не только новый HUD. Исправлено — `AddText` теперь при наличии `\n` делит на строки и раскладывает их с учётом вертикального `TextAnchor` (Upper/Middle/Lower), однострочный путь (`AddSingleLineText`) не менялся, чтобы не трогать уже отрисованные без бага места.
- **Эмодзи в заголовках не работают, а обычные символы — работают** (измерено на живой игре через мост, не предположение). Фактический шрифт — `LegacyRuntime` (фоллбэк `Font.CreateDynamicFontFromOSFont`, т.к. `Resources.GetBuiltinResource<Font>("Arial.ttf")` тут не отдаёт нужного). Покрытие проверено `GetCharacterInfo`:
  - **Есть всё**: латиница, кириллица, `[]{}()<>|/\+-=_*#@$%&!?.,:;'"`, цифры, и символы `→ ← • · × … ▶ ◀ ⏸ ▌ ★ ☆ ✓ ✗ ■ ● ◆ ▲ ⚙`. Их использовать МОЖНО (прежняя заметка «дингбаты не гарантированы» была неверной).
  - **Нет эмодзи** (🧍/🎯/🎵 и т.п.): это суррогатные пары, `AddText` перебирает `char`-ы, и каждая половина отдельно резолвится в notdef — рисуется пустота, но отступ съедается. Именно поэтому префиксы вкладок и заголовков виджетов выглядели «съехавшими». Убраны; вместо них — векторные фигуры (`CustomGui.Circle`/`Rect`/`Triangle`) либо перечисленные выше настоящие символы.
- **Новые примитивы в `CustomGui`**: `RectGradient` (вертикальный градиент, per-vertex цвет), `Circle` (скруглённый rect с rounding = половина размера — дуги сходятся в окружность), `Triangle` (произвольный треугольник, для play/pause-подобных иконок).
- **Обрезка текста обязательна**: у рендерера НЕТ scissor-прямоугольника, длинная строка рисуется прямо поверх соседних элементов и дальше за панель — в игровой мир. Для этого есть `CustomGui.MeasureWidth`/`MeasureText` (сумма advance'ов, тот же обход, что в `AddSingleLineText`) и `CustomGui.TextClipped`, обрезающий с многоточием по ширине прямоугольника. Через него уже идут `SectionHeader`, подписи строк меню, имена модулей и `LiveInfo`. Любой новый текст неизвестной длины (путь, ник, статистика) рисовать только через `TextClipped`.
- **Плеер в HUD читает реальный трек из Spotify** (`Win32.GetSpotifyWindowTitle()`) — НЕ через `Windows.Media.Control` (WinRT/COM API для системного "sейчас играет"): плагин работает под Mono-рантаймом Unity (BepInEx 5, не IL2CPP/.NET), а Mono-поддержка WinRT-активации неполная — риск зависания/краша всего процесса, тот же класс риска, что и с преждевременным касанием `PhotonNetwork` (см. выше). Вместо этого — обычный `user32.dll` P/Invoke (`FindWindow("SpotifyMainWindow", null)` + `GetWindowText`), тот же безопасный паттерн, что уже используется в `Win32.cs` для клавиш. Заголовок окна Spotify = `"Spotify"` когда пауза/ничего не играет, `"Artist - Track"` когда играет — позиции/длительности трека в заголовке нет, только статус играет/нет.
- **`EspOverlay.ResolveInventory(PlayerAvatar)`** (публичный метод, добавлен в этой сессии) — расширение уже существовавшего hash-based резолвера инвентаря (`StatsManager.playerInventorySpot1/2/3` → hash → `ItemAttributes.instanceName` в сцене), теперь возвращает ещё и `ItemAttributes.icon` (подтверждённое публичное поле `Sprite`, заполняется `CreateIconFromRenderTexture`/`LoadSpriteFromFile`) — используется HUD-виджетом «Цель» для реальных иконок предметов в инвентаре другого игрока.

## Автономный цикл тестирования (мост + запуск + логи)

Сессия может тестировать чит сама, без участия пользователя. Три составные части:

- **`DebugBridge.cs`** — раз в 250 мс читает `BepInEx/plugins/RepoCheatMenu_Bridge/command.txt`, выполняет содержимое как C# через `ScriptEngine` (тот же, что вкладка «Скрипты»), пишет ответ в `result.txt`. Тумблер `CheatState.DebugBridgeEnabled`, по умолчанию выключен. Скрипт-обёртка: `scratchpad/bridge.sh`.
  - `ScriptGlobals` отдаёт скрипту только ПУБЛИЧНУЮ поверхность, а `CheatState`/`CustomOverlayUI`/`PanicHack` — `internal`. Достаются рефлексией: `typeof(ScriptGlobals).Assembly.GetType("RepoCheatMenu.CheatState").GetField("HudEnabled")`, дальше `.GetValue(null)` и свойство `Value` у `ConfigEntry`. Работает и на чтение, и на запись.
  - Кириллицу и вложенные кавычки в bash-строке не передавать — писать команду в файл (`cmd.csx`) и подавать как `"$(cat cmd.csx)"`.
  - Дедупликация команд идёт по времени записи `command.txt`, НЕ по тексту. Раньше сравнивался текст — и повторный одинаковый запрос (нормальное дело при опросе значения во времени) молча отбрасывался, вызывающая сторона видела только таймауты.
- **Запуск игры**: r2modman подменяет НЕ переменные окружения. Ключи, которые реально понимает местный Doorstop (вытащены строками из `winhttp.dll`): аргументы командной строки `--doorstop-enabled` / `--doorstop-target-assembly`, плюс `doorstop_config.ini` рядом с `REPO.exe`. **Аргументы командной строки проигрывают INI** — проверено, игра всё равно грузила BepInEx из папки игры. Рабочий способ: прописать в `doorstop_config.ini` абсолютный `target_assembly=<профиль>\BepInEx\core\BepInEx.Preloader.dll`. Сейчас так и сделано, бэкап — `doorstop_config.ini.claude-backup`. **Побочный эффект**: запуск игры напрямую из Steam теперь тоже грузит чит-профиль.
  - В папке игры (`steamapps/common/REPO/BepInEx/`) лежит СТАРАЯ копия мода, оставшаяся от ручного копирования из архива. Пока INI не переключён на профиль — грузится именно она, и правки «не появляются». Проверять по `Event logs:`-строке в логе и по дате DLL.
- **Скриншот**: `PrintWindow` через PowerShell + `System.Drawing` работает на этой игре (кадр реальный, не чёрный). Годится для визуальной сверки HUD/меню. **Синтетические нажатия клавиш не работают** — Windows не даёт фоновому процессу забрать фокус, `keybd_event` уходит в активное окно (проверено: F6 ушёл в VS Code). Кликать по меню за пользователя нельзя; всё состояние менять через мост.
- Готовый цикл целиком: `scratchpad/cycle.ps1` (закрыть → задеплоить → запустить → включить HUD → снять кроп 2x). В `.ps1` не класть кириллические литералы — Windows PowerShell 5.1 читает файл как ANSI без BOM и путь ломается; путь к DLL резолвится вайлдкардом.

**`EventLog.cs`** — свои логи по категориям в `BepInEx/plugins/RepoCheatMenu_Logs/<дата_время>/`: `spawn` (что, каким путём, в какие координаты), `teleport` (откуда→куда), `items` (кража из рук), `bridge`, `session`, плюс `all` одним потоком. Буфер сбрасывается раз в 2 сек и принудительно при выходе/панике. Точка перехвата спавнов — `NetSpawn.Spawn`, через неё идут все спавны мода разом.

## Найденные баги (подтверждены на живой игре)

- **Паника глушила сам мост** (найдено при попытке проверить фикс персистентности): `DebugBridge.Apply()` тикает внутри `ApplyStats`, а тот целиком отключается строкой `if (PanicHack.Hidden) return;`. Итог: «ВЫКЛ» + выход = сессия, из которой можно выбраться ТОЛЬКО физическим нажатием `]` (синтетику Windows не пропускает). Починено двумя частями: (1) мост вынесен перед этим гейтом и тикает при `Hidden`, если его собственный тумблер включён — по той же логике, по которой там уже особым случаем опрашивается `]`; (2) в `PanicHack` появился `NeverSwept` — паника больше не гасит `DebugBridgeEnabled`/`EventLogging` (отладочная обвязка) и `HudAutoStack`/`HudMediaPlayerUseSpotify` (настройки вида, а не читы; сам HUD и так скрыт через `HudEnabled`).
  - Круг проверен целиком: включить тумблеры → паника (мост жив) → убить игру → перезапуск (`Hidden=True`, тумблеры off, мост отвечает) → `Reactivate()` → всё вернулось.
- **`PanicHack` терял настройки навсегда**: гасил все ~131 `ConfigEntry<bool>` (значения сразу пишутся на диск), а список «что было включено» держал только в памяти. Выход из игры после «ВЫКЛ» → всё выключено, `]` в новой сессии не знает даже, что было спрятано. Починено: снапшот и флаг persist в конфиг (секция `[Panic]`), `PanicHidden` исключён из собственной зачистки.
- **`PublicGameHack.JoinRandomPublic` не работал никогда**: гвард `if (PlayerAvatar.instance != null) return;`. Замерено вживую — в главном меню (`levelCurrent = "Level - Main Menu"`) этот объект СУЩЕСТВУЕТ («Player Avatar Controller», превью персонажа), поэтому гвард срабатывал всегда. Правильная проверка — `SemiFunc.MenuLevel()`. После фикса заход в публичную игру отработал с первой попытки.
  - Общее правило: `PlayerAvatar.instance == null` НЕ означает «мы в меню». Для этого есть `SemiFunc.MenuLevel()` / `RunIsLevel()`.
- **`FlyHack` не проходил сквозь стены**: `isKinematic` и `col.enabled` писались ТОЛЬКО на переходе (`if (wantKinematic != _wasKinematic)`), а игра переустанавливает их под себя каждый кадр. После первого применения флаг `_wasKinematic` больше не менялся, и мод их не возвращал. Замерено на живой игре при включённом полёте: `useGravity=False` (пишется безусловно каждый кадр — держится), но `isKinematic=False`, `collider=True` — то есть полёт двигал позицию, но коллизия оставалась. ## Ту же дыру, что у Revive/Flip - поиск по всему RPC-каркасу игры (2026-09-08)

Нашли новую фичу тем же методом, каким сделаны Revive Self и Flip - не копированием из GameTools, а прямым grep'ом декомпила игры на "`SemiFunc.MasterOnlyRPC(_info)` без доп. проверки отправителя" (для RPC) и "`OnPhotonSerializeView`" (для спуфинга broadcast-полей). Сотни методов в игре имеют этот же дырявый гейт (Arena/ArenaRace/traps/enemies - в основном служебные state-машины конкретных сущностей, не general-purpose). Найдена и реализована:

- **`EnemyFreezeHack.cs` / `CheatState.FreezeEnemies` + `FreezeEnemiesRange`** - `Enemy.FreezeRPC(float time, PhotonMessageInfo _info = default)` защищён ТОЛЬКО `MasterOnlyRPC`, как Revive. `Enemy.FreezeTimer` (публичное) реально держит врага на месте - `EnemyRigidbody.cs` зануляет velocity/angularVelocity и выходит из movement/chase, пока таймер > 0 (подтверждено в декомпиле). Работает для гостя и хоста. Проверено вживую через мост: `FreezeTimer` держится на 2.0, не утекает, лог чист.

**Найдены и исправлены два реальных бага при верификации:**
1. **`EspOverlay.cs` DrawEnemies - ESP врагов молча не работал.** `GameReflect.Get<Enemy>(parent, "enemy")` (строчная "e") - реальное имя поля в текущей версии игры **`Enemy`** (заглавная), подтверждено вживую перебором полей через мост. `GameReflect.Get` не бросает исключение при промахе имени - тихо возвращает `default`, `if (enemy == null) continue;` просто пропускает каждого врага без единой ошибки в логе. Неизвестно, с какого именно апдейта игры регистр сменился - `PillarDropHack.cs`/`TeleportHack.cs` уже использовали правильное `"Enemy"`, только `EspOverlay.cs` был на старой строке.
2. **`GameReflect.Invoke` на Mono не подставляет значение по умолчанию для последнего необязательного `PhotonMessageInfo _info = default(...)` параметра** - `MethodInfo.Invoke` требует ровно столько аргументов, сколько объявлено параметров, иначе `TargetParameterCountException`. Ловится ТОЛЬКО в сингловом/host-branch (в мультиплеере идёт настоящий `photonView.RPC(...)`, а не reflection) - значит баг молчит, пока фичу не тестируют соло. Нашли на новом `EnemyFreezeHack.cs`, но по этому же паттерну задним числом починили **`MassRaidHack.cs`** и **`RaidHack.cs`** (дважды) - все три звали `RequestSeatRPC` без финального `default(PhotonMessageInfo)`. Проверил ОСТАЛЬНЫЕ `GameReflect.Invoke(..., "XxxRPC", ...)` по всему проекту сверкой с декомпилом сигнатур - `HealOtherRPC`/`TumbleImpactRPC`/`MusicKeyPressedRPC`/`RPC_StartUnequip`/`RPC_RequestEquip`/`OnHurtPlayerRPC`/`DiscoverRPC`/`TrapStopRPC` у игры реально НЕ ИМЕЮТ трейлинг-`PhotonMessageInfo` в сигнатуре - эти вызовы были правильными изначально, ложной тревоги нет. `UtilityHolesHack.cs`/`WorldHolesHack2.cs` уже и раньше делали это верно.

Урок на будущее: при добавлении НОВОГО `GameReflect.Invoke(..., "XxxRPC", args...)` - всегда сверять полную сигнатуру RPC-метода в декомпиле, и если там есть `PhotonMessageInfo _info = default(...)`, передавать `default(PhotonMessageInfo)` явным последним аргументом, а не полагаться на то, что reflection сам подставит default.

## Third Person: два реальных бага, найденных вживую, и один опасный тупик (2026-09-08)

Пользователь поймал вживую (играя с другом): (1) тумблер Third Person не выключался, "всегда в третьем лице"; (2) захват предметов в третьем лице шёл от смещённой камеры, а не от прицела.

**Баг 1 - причина подтверждена вживую через мост**: `VisionHack.cs` сбрасывал камеру в `Vector3.zero` при выключении. Замерил напрямую: настоящий покой-локал камеры - `~(0, 0.46, -2.0)`, НЕ ноль. Сброс в ноль уводил камеру в другую, тоже неправильную точку - воспринималось как "тумблер не работает". Фикс: `_backupCamLocalPos` - настоящий backup/restore вместо жёсткого нуля, тот же паттерн что у DinnerBone/Flip.

**Баг 2 - причина подтверждена вживую**: `PlayerLocalCamera.GetOverrideTransform()` (декомпил) - это КАНОНИЧЕСКИЙ аксессор "куда целится игрок", читается ВЕЗДЕ (grab/инструменты/оружие/техника/ИИ врагов - подтверждено grep'ом по всему декомпилу). В обычном режиме возвращает `PlayerLocalCamera.transform`, который каждый кадр копирует `CameraNoise.Instance.transform` (подтверждено в `PlayerLocalCamera.Update()`) - а `CameraNoise.Instance` сидит на том же объекте что `Camera.main`, так что наш third-person offset тащит за собой и точку прицеливания. Фикс - `ThirdPersonAimPatch` в `Patches.cs`: Harmony-постфикс на `GetOverrideTransform()`, подставляет прокси-transform на `VisionHack.TrueAimPosition/TrueAimRotation` (реконструированную настоящую позицию, независимую от смещённой камеры) - **только для чтения**, не трогает физику игрока. Проверено вживую: `GetOverrideTransform().position` реально отличается от смещённой камеры.

**ОПАСНЫЙ ТУПИК, не повторять**: пробовал переписать Third Person на штатный `CameraPosition.instance.OverridePosition(Vector3, float time)` (декомпил `CameraPosition.cs`) - у игры ЕСТЬ родной API для временного смещения камеры, который сам зовёт `PhysGrabber.SetThirdPerson(true)`/`FlashlightController.SetThirdPerson(true)` (реальный игровой third-person, используется для какой-то встроенной фичи типа "рассмотреть предмет вблизи"). Выглядело идеально - но при вызове **каждый тик** (чтобы держать активным неопределённо долго, а не как задумано - кратким "peek" с автоматическим истечением по таймеру) через несколько секунд **РЕАЛЬНАЯ позиция игрока** (`PlayerController.transform.position`, не только камера) улетела в свободное падение - замерено вживую через мост: Y дошёл до -5810, затем -17052, затем -69729, `PlayerAvatar.instance` стал `null` (аватар уничтожен). Это НЕ визуальный баг - персонаж реально проваливается сквозь уровень. Причина не выяснена (возможно light-culling/audio-restart/particle-restart логика внутри `PositionOverrideToggled`, рассчитанная на кратковременный вызов, ломается при бесконечном keep-alive). **Не использовать `CameraPosition.OverridePosition()` в режиме "держать активным долго"** - откатил обратно на прямую запись `Camera.main.transform.localPosition` (с фиксом бэкапа выше) + отдельный `ThirdPersonAimPatch` для прицела. Если когда-нибудь захочется вернуться к нативному API - сначала выяснить, что именно в `CameraPosition`/`PositionOverrideToggled` вызывает падение, при КОРОТКИХ, редких вызовах (как игра сама его использует), а не при непрерывном тике.

## Мигание камеры от третьего лица - реальный баг, найден и подтверждён пользователем (2026-09-10)

## Маскировка скина под хоста / MimicHostSkin (2026-09-11)

## Пятый и шестой баги того же захода: Escape никогда не закрывал меню, и почему (2026-09-12)

Продолжение автономного прохода "фикси баги" (см. секцию выше). Аудит `KeybindManager.cs`/`Win32.cs` (система биндов и опрос клавиатуры/мыши напрямую через `GetAsyncKeyState`, раз `UnityEngine.Input` в этой игре не репортит нажатия надёжно).

5. **`Win32.ToVirtualKey(KeyCode)` не знал про `KeyCode.Escape`** - падало в `default: return 0`, а `IsKeyDown` коротко возвращает `false` при `vk==0`. При этом Escape для ОТМЕНЫ захвата бинда (в `KeybindManager.Apply()`) работал всегда - та ветка зовёт `Win32.WasVkPressed(0x1B)` напрямую, минуя этот свитч вообще, поэтому один и тот же баг задел только один из двух путей, использующих одну и ту же клавишу.
6. **Тот же свитч в принципе не покрывал большую часть `KeyCode`** - `Plugin.MenuKey` (клавиша открытия САМОГО меню) это обычный `ConfigEntry<KeyCode>`, пользователь может выставить туда любое из ~150 значений через конфиг-файл BepInEx. Если бы кто-то перебиндил `MenuKey` на что угодно из этого списка - единственный хоткей, открывающий всё меню целиком, молча переставал бы работать, без объяснения почему. Расширено покрытие под реалистичный набор клавиш, которые человек реально мог бы выбрать (не пытался закрыть буквально все ~150 значений enum'а - джойстик-кнопки и т.п. бессмысленны как хоткей меню).

Оба фикса - только в [Win32.cs](RepoCheatMenu/Win32.cs) (`ToVirtualKey`), никакой другой файл не менялся. Собрано (`0 Warning(s), 0 Error(s)`), задеплоено. Живьём не проверено - см. причину в секции про авто-реконнект ниже (игра намеренно не перезапускалась в этом заходе).

1. **`AnimSpeedSpoof`/`AnimSpeedValue`** ([AnimSpeedHack.cs](RepoCheatMenu/AnimSpeedHack.cs), вкладка "Тролль") - `PlayerAvatar.OverrideAnimationSpeedActivateRPC` задаёт скорость проигрывания Animator'а твоего аватара у всех остальных. Приёмная сторона сама себя продлевает каждый кадр (`OverrideAnimationSpeedLogic`, ветка `!isLocal && overrideAnimationSpeedActive`), поэтому хватает ОДНОГО вызова на изменение, без пере-отправки по тику; их re-arm не может улететь обратно к нам (их обёртка-отправитель под `if (isLocal)`, а наш аватар им не локальный). Вниз по течению только `animator.speed` и собственный `deltaTime` визуалов - ни Transform, ни Rigidbody. Выше ~3x их же пружинная математика (её deltaTime умножается на тот же множитель) начинает перелетать и аватар зримо дёргается - это их рендер нашей модели, не физика, и на такой настройке это скорее фича.
2. **`AllEyesOnMe`** ([AllEyesHack.cs](RepoCheatMenu/AllEyesHack.cs), вкладка "Тролль") - самая необычная из всех: `PlayerVoiceChat.IsTalkingRPC(bool)` транслирует "я сейчас говорю". Грепнул ВСЕХ потребителей этого флага в декомпиле - их трое и все визуальные: **`PlayerEyes.Update()` заставляет каждый аватар в радиусе 6 м навести ГЛАЗА на того, кто говорит** (`currentTalker`), плюс индикатор "говорит" в списке игроков лобби и реакция головы в меню. Аудио не трогается вообще - весь микрофонный/стримовый код сидит под `if (photonView.IsMine)`. Итог: все вокруг постоянно провожают тебя взглядом, при полной тишине.
   - **Почему тут нужна пере-отправка раз в 0.5с, в отличие от двух фич выше**: собственный отправитель игры edge-triggered (`if (isTalking != isTalkingPrevious) photonView.RPC(...)`), и в момент, когда твой настоящий микрофон закрывается, он шлёт честный `false`, затирающий наш спуф. Пере-заявляем своё значение раз в интервал.
   - **Важная деталь, которая спасла от бага взаимодействия**: игра шлёт этот RPC на `RpcTarget.Others`, НЕ на `All` - и мы шлём так же. Поэтому наш локальный `isTalking` остаётся честным, и `InvisibleRevealWhileTalking` (который читает ровно это поле локально) продолжает работать как раньше. Если бы отправляли на `All`, невидимка с включённым тем тумблером палила бы позицию непрерывно.

**Отсеяно по тому же гостевому фильтру (работает только у хоста, пользователю бесполезно)**: `StartEasterEggRobeRPC` (`ValuableBoombox` - подменяет музыку бумбокса на секретный трек, милая пасхалка, но `MasterOnlyRPC`), `MaterialEffectOverrideRPC` (`PlayerHealth` - цветная подсветка тела, тоже `MasterOnlyRPC`), `CrownPlayerRPC`, `ExplosionRPC` и вся прочая мастер-часть списка. Если когда-нибудь будешь хостить - вернуться сюда, там есть что взять.

**Тупик, проверен и закрыт**: `HealedOtherRPC` (`PlayerAvatar`) - единственный найденный RPC СОВСЕМ без гейта, звучал многообещающе, но внутри только `if (isLocal) TutorialDirector.instance.playerHealed = true;` - выставляет флаг туториала и всё. Ничего не даёт, не возвращаться.

## Седьмая и восьмая фичи - самые "легальные" из всех (2026-09-13, продолжение)

Продолжение прохода по 17 `OwnerOnlyRPC`-кандидатам (гостю доступны честно). Обе новые фичи не спуфят вообще ничего - зовут публичные методы самой игры, а синхронизацию игра делает за нас своим же кодом.

1. **`EyeOverride`/`EyeOverrideState`** ([EyeOverrideHack.cs](RepoCheatMenu/EyeOverrideHack.cs), вкладка "Косметика") - `PlayerHealth.EyeMaterialOverride(state, time, priority)`, ПУБЛИЧНЫЙ метод, которым игра сама пользуется из `ChatManager` (Love/Red/Green на события чата), `GumballValuable` (Inverted) и `EnemyCeilingEye` (CeilingEye). Пять готовых видов глаз: Red, Green, Love, CeilingEye, Inverted.
   - **Ключевое отличие от уже существующего `EyeColor`**: тот пушит фиксированную палитру через НАШ собственный `RCM_`-канал custom-properties, поэтому его видят только игроки с этим же модом. А этот - штатный эффект на штатном канале игры (`PlayerHealth.Update` сам шлёт `EyeMaterialOverrideRPC` на `RpcTarget.Others` по фронту), значит его видят ВСЕ в комнате, хоть с модом, хоть без. По охвату строго лучше.
   - Перезаряжается по таймеру (метод ставит обратный отсчёт, не защёлку). Выключение - просто перестать перезаряжать: игра сама разошлёт деактивацию И сама сбросит `overrideEyePriority` в -999 (подтверждено в её `Update`), поэтому наш высокий приоритет (2, выше игровых 0/1) не останется висеть и не задавит легитимные игровые эффекты после выключения.
2. **`DemonVoice`** ([DemonVoiceHack.cs](RepoCheatMenu/DemonVoiceHack.cs), вкладка "Голос") - **единственный голосовой трюк в моде, который другие реально СЛЫШАТ**. `ChipmunkVoices` рядом перепитчивает ИХ голоса в ТВОИХ ушах (чисто playback, ничего не уходит с машины), а этот - наоборот. `ItemGunTranq.MakeHitPlayersHigh()` - публичный метод транк-пушки, который применяет её эффект попадания к `PlayerAvatar.instance`: расширяет зрачки и шлёт `SlowDownVoiceRPC` всем остальным, а у них выполняется `voiceChat.OverridePitch(0.65f, 1f, 1f, 3f, 0.1f, 20f)` на их копии твоего голоса - 0.65x с медленным колебанием, три секунды.
   - Приёмный гейт - `SemiFunc.OwnerOnlyRPC(_info, playerAvatar.photonView)` против аватара, чей ViewID пришёл в пейлоаде, а метод всегда подставляет `PlayerAvatar.instance` - то есть нас, чей аватар наш. Проходит честно, гость или хост, без байпаса.
   - **Ограничение, неустранимое, потому что едем по рельсам самой игры**: RPC объявлен на компоненте `ItemGunTranq`, значит в уровне должен существовать экземпляр транк-пушки (держать и стрелять не надо, просто существовать) - иначе PUN не разрешит вьюху. Если её нет - спавним через существующий спавнер предметов во вкладке "Мир". Статус показывается строкой LiveInfo под тумблером, по образцу GhostRider.
   - Пере-отправка раз в 2.5с - у них это 3-секундный обратный отсчёт (`overridePitchTimer`), не защёлка.
   - Безопасность: `OverridePitch` трогает только `audioSource.pitch` под своим затухающим таймером, и близко не подходит к `ToggleMixer`/AudioMixer-роутингу - именно про него предупреждение в `VoiceFilterHack.cs` про трижды сломанный голос. Плюс выполняется на ЧУЖИХ машинах, не на нашей.

## Сессия 2026-10-04: комнаты, ноклип, дальность, текст песни, оптимизация (собрано, НЕ задеплоено и НЕ проверено живьём - игра была запущена)

1. **Пропадающие комнаты (`MultiRoomHack.cs`, переписан).** Причины, найденные по декомпилу игры и по LateJoinNow/Late_Join:

Старый код выходил, потом `JoinRoom(домой)` - возвращаться было некуда. Теперь отказ, если в комнате кто-то ещё; последняя созданная комната - та, в которой вы остаётесь.

## Горячая перезагрузка мода без перезапуска игры (2026-10-04) - написано и собрано, НЕ установлено и НЕ проверено в живой игре

Зачем: деплоить правки, пока игра запущена, чтобы она подхватывала новую сборку сама. Схема как у BepInEx ScriptEngine, проверена по декомпилу BepInEx (`BaseUnityPlugin` умеет жить вне chainloader'а - сам собирает `Info`; `ConfigFile` не следит за файлом; chainloader сканирует только `*.dll`, плагины добавляет через `ManagerObject.AddComponent`).

- **`RepoCheatMenu.Loader/`** (`RepoCheatMenu.Loader.dll`, ~14 КБ, знает только BepInEx и Unity) - единственный файл, который грузится обычным путём и НЕ обновляется на лету; должен меняться почти никогда.
- **Ядро** - это наша обычная `RepoCheatMenu.dll`, но на диске лежит как **`RepoCheatMenu.core`** (не `.dll`, иначе chainloader запустит вторую копию мода). Загрузчик читает файл в память (`Assembly.Load(byte[])`, файл не блокируется) и добавляет тип `RepoCheatMenu.Plugin` на скрытый объект `RepoCheatMenu_Host`.
- **Порядок замены** (чтобы плохая сборка не оставила без мода): 1) претест новых байтов (загружаются, есть тип `Plugin`, есть флаг `Plugin.Ready`) ДО того как трогать работающую копию; 2) ждать безопасный момент - работающее ядро отдаёт `Plugin.HotReloadBlocker` (`null` = можно; иначе причина: идёт Sibling Rooms, генерируется уровень, смена сцены), до 90 с; 3) `Destroy(host)` -> `Plugin.OnDestroy` снимает Harmony, закрывает меню, откатывает оптимизацию, убирает объекты `RepoCheatMenu_*` и `EspChamsGhost`; 4) старт нового; если `Awake` не дошёл до `Ready = true` - уничтожить и поднять прошлые рабочие байты (статус `rolled-back`).
- **Защита от недописанного файла:** изменение принимается, только если размер+время не менялись целый опрос (раз в секунду); скрипт деплоя пишет во временный файл и переименовывает.
- **Тики загрузчика:** `BaseUnityPlugin.Update` в этой игре не срабатывал (см. заметки выше), поэтому свой `Ticker` на отдельном объекте + запасной `Application.onBeforeRender`; в `hot-status.json` пишется, какой источник сработал (`tickSource`).
- **Статус:** `hot-status.json` рядом с загрузчиком: `state` (`loaded`, `waiting`, `reloaded`, `failed`, `rolled-back`, `dead`, `conflict`, `no-core`), `message`, `coreVersion`, `reloadCount`, `time`. Скрипт деплоя ждёт его и печатает вердикт.
- **Конфликт:** если мод ещё стоит как обычный плагин (`RepoCheatMenu.dll`), загрузчик через кадр видит это в `Chainloader.PluginInfos` и остаётся неактивным (`conflict`), чтобы не запустить мод дважды.
- **`ScriptEngine.FindAssemblyFile`** теперь ищет и `RepoCheatMenu.core` (Roslyn-скриптам нужна ссылка на файл мода на диске).
- **`tools/deploy.ps1`**: `powershell -File tools\deploy.ps1` (сборка + деплой в ОБЕ папки; при запущенной игре и установленном загрузчике ждёт вердикт, коды выхода 0 ок, 1 ошибка, 2 ничего не сделано), `-NoBuild`, `-Legacy` (вернуть обычную установку одним `RepoCheatMenu.dll`, игра закрыта). ## Скрыть себя из списка игроков - повторный разбор (2026-10-13), вывод прежний, но найден ТЕХНИЧЕСКИ возможный «призрак»
Списки: лобби `MenuPageLobby` (раз в 1 с берёт `SemiFunc.PlayerGetList()`, фильтров нет, сортировка по ViewID) и `MenuSpectateList` (те же аватары, но только `isDisabled`, т.е. мёртвые). Аватар попадает в `GameDirector.PlayerList` в `PlayerAvatar.Awake` (строка ~304) на КАЖДОМ клиенте при получении Instantiate, там же гвард «второй аватар того же Owner - Destroy». Спуфить нечего: это не поле, а сам факт наличия объекта.
Что проверено заново: `NetworkManager.Start` делает `PhotonNetwork.Instantiate(playerAvatarPrefab)` и отдельным RPC `PlayerSpawnedRPC` сообщает хосту «готов» (хост ждёт `instantiatedPlayerAvatars >= CurrentRoom.PlayerCount`, считает по Sender, НЕ по аватарам). Остальные «готов»-счётчики (ModulesReady, EnemyReady, valuableSpawnPlayerReady, ReloadScene.PlayersReady) тоже на RPC по Sender. Значит хост от отсутствия аватара не зависнет.
Единственный обход: не рассылать Instantiate аватара (или послать остальным сырое событие Destroy 204, оставив свой объект) - «призрак»: в списках и в PlayerList у других вас нет вообще. ## Баги невидимки: velocity, grace, exception safety (2026-10-15, v1.0.103) — задеплоено в 3 профиля + Steam\local-RepoCheatMenu

- **`InvisiblePatch.Postfix` -> `[HarmonyFinalizer] Finalizer`**.
